# CodeCraft Studio — Render deployment package

A subscription-gated browser coding workspace built around the OpenCode headless server. The app includes account registration/login, an admin dashboard for per-user API settings and account suspension, a paid monthly membership flow via Stripe Checkout, verified subscription webhooks, a private project workspace per account, project file upload/download, a persistent project prompt, and the supplied yellow-cube thinking animation.

The browser UI intentionally does not display model-provider names, model identifiers, gateway URLs, or credentials. API settings are configured in `/admin` per account. Keys are encrypted with `APP_ENCRYPTION_KEY` at rest and never returned by admin APIs; optional shared fallback settings can be supplied in private Render environment variables.

## Included

- `server.js`: Express application, SQLite persistence, account auth, admin routes, encrypted per-user API credentials, subscription validation, Stripe integration, OpenCode server manager, private provider gateway, and workspace upload/export endpoints.
- `opencode/system-prompt.txt`: persistent engineering instructions applied to the OpenCode build agent.
- OpenCode's built-in tools are allowed, Exa web search and experimental LSP tool are enabled, and common language servers are installed for TypeScript/JavaScript, Python, HTML/CSS/JSON, YAML, and Bash. Built-in agents remain available; CodeCraft also adds reviewer, tester, and researcher subagents plus three global skills. Admins can optionally configure local or remote MCP servers per user; their JSON and secrets are encrypted at rest.
- The Docker build checks that the OpenCode CLI and `serve` command exist. This verifies installation during image build, not a real provider call; test a task after deploying because model APIs differ in their tool-calling support.
- `public/yellow-cube-v3.html`: adapted from the uploaded animation and shown while a task runs.
- `public/index.html`, `public/styles.css`, `public/app.js`: responsive Arabic UI.
- `Dockerfile` and `render.yaml`: Render deployment blueprint with a persistent disk.

## Render setup

1. Push this folder to a GitHub repository.
2. In Render, create a Blueprint from that repository and review `render.yaml`. This blueprint uses a paid Starter web service and a persistent disk because subscriber accounts, subscriptions, workspaces and chat history must survive restarts. Confirm the current plan and disk cost in Render before creating it.
3. Set the private environment variables in the Render service:
   - `ADMIN_EMAIL`: the owner account that should receive admin privileges.
   - `ADMIN_PASSWORD`: unique password, at least 14 bytes. It is used to bootstrap/reset the owner account at service startup.
   - `APP_ENCRYPTION_KEY`: automatically generated by `render.yaml`; keep it unchanged or previously saved API keys will no longer decrypt.
   - `APP_URL`: the exact public service origin, e.g. `https://your-service.onrender.com`.
   - Optional `AI_BASE_URL`, `AI_MODEL_ID`, `AI_API_KEY`: a shared fallback for accounts without a custom API; custom per-user settings are managed at `/admin`.
   - `STRIPE_SECRET_KEY`: Stripe secret key, initially a test-mode key.
   - `STRIPE_WEBHOOK_SECRET`: signing secret for the webhook endpoint described below.
   - `STRIPE_PRICE_ID_MONTHLY`: the Stripe Price ID configured for a recurring subscription.
   - `SUBSCRIPTION_DISPLAY_PRICE`: friendly customer-facing price text; use the same amount/currency configured in Stripe.
4. In Stripe, create a recurring product/price and configure a webhook destination at `https://your-service.onrender.com/api/stripe/webhook`. Subscribe to at least `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, and `invoice.payment_failed`. Copy the webhook signing secret into Render.
5. Configure the Stripe Customer Portal in the Stripe Dashboard if customers should manage/cancel memberships themselves.
6. Deploy and check `https://your-service.onrender.com/healthz`. Register a test account, start Checkout in Stripe test mode, complete the test payment, and wait for the signed webhook to activate the membership. Never activate a membership based only on the browser redirect.
7. Before accepting live payments, switch Stripe to live mode and replace the price ID and keys with the matching live values. Test subscription cancellation, failed payments, repeated webhook events, and service restarts.

## Local development

- Install Node.js 22+, the OpenCode CLI (`npm install -g opencode-ai`), Git, Python 3, and build dependencies.
- Copy `.env.example` to `.env`; set private values. Never commit `.env`.
- Run `npm install`, then `npm start`.
- The app expects the `opencode` command to be available. The Docker build installs it automatically.

## Important operational notes

- OpenCode runs as a headless service and is managed by the app. Each subscriber gets a separate Unix identity, private home/config, and workspace. The upstream model credential and Stripe secrets are kept in the root-owned web process; the coding worker gets only a per-user token for a loopback gateway. The gateway injects the upstream credential and rewrites the internal model alias server-side.
- OpenCode built-in tools are enabled, including file edits, shell commands, web search where supported, and experimental LSP tool support. Reviewer/tester/researcher subagents and `code-review`, `web-research`, and `test-debugging` skills are seeded in each user's OpenCode home. Admin can set encrypted per-user MCP definitions for local or remote servers in `/admin`; the service does not silently install third-party MCP servers without admin configuration. The per-user Unix UID/workspace separation is a useful boundary, but it is **not a complete container sandbox**: shell tools can execute user-provided code and make outbound network requests. For a large public SaaS, add per-task containers/VMs, CPU/memory/process limits, outbound-network controls, queueing, usage quotas, abuse monitoring, and a security review before offering unrestricted execution to arbitrary customers.
- The app currently uses SQLite on the persistent disk. A single Render instance is intended; do not scale horizontally with this SQLite design. For multiple app instances, migrate user/session data to managed PostgreSQL and put workers/queues in separate services.
- The model provider may throttle or fail independently. The browser receives a generic user-facing message; detailed diagnostic errors are logged server-side without returning provider responses to customers.
- Upload skips typical secret files such as `.env`, private keys, and `.git`/dependency folders. Review project files before asking an AI coding agent to handle highly sensitive source.
- The animated cube is a work-in-progress indicator only; it does not expose private reasoning or guarantee progress.

## Security checklist before live launch

- Use a strong generated `SESSION_SECRET` and keep all keys in Render environment settings.
- Turn on Stripe webhook signature verification (already implemented) and keep the webhook secret private.
- Keep the OpenCode HTTP servers bound to `127.0.0.1`; never expose their dynamic ports publicly.
- Set usage limits compatible with the upstream provider's real limits and the price you charge.
- Add email verification, password reset, terms/privacy policy, backups, monitoring, abuse reporting and legal/business review before public launch.


OpenCode is installed during the Docker image build (not manually uploaded): the Dockerfile installs `opencode-ai` globally and checks `opencode --version`. At request time the server launches `opencode serve` on loopback for the subscriber workspace. The post-login workspace is a full-screen chat with the supplied animated thinking indicator; file upload/download controls live inside the composer.


## Admin and per-user API

Set `ADMIN_EMAIL`, `ADMIN_PASSWORD` (14+ bytes), and a stable `APP_ENCRYPTION_KEY`. The configured admin account is created/updated from these environment variables on startup. Sign in on the main page and visit `/admin` to select each account, set its OpenAI-compatible API base URL and model ID, enter an API key, or suspend the account. The API key is encrypted using AES-256-GCM and is never returned by the admin API. If `APP_ENCRYPTION_KEY` is changed after saving credentials, those credentials cannot be decrypted; preserve this value in Render.

- The chat can display a compact summary of tool names returned in the OpenCode response; it does not expose raw tool inputs, outputs, or secrets.
